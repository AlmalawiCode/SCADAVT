1 The idea in one sentence

You draw a network of controllers on a canvas — and the picture you draw is the file the engine runs. One MTU (the master) reads the sensors of many PLCs and, following your rules, sends commands back to them. Everything on a switch can talk; a router joins two switches.

A typical network: the MTU and all PLCs connect to one switch (one LAN), so the MTU can reach every PLC.

2 The four parts

Four node types. Each PLC becomes a real emulated machine running a Modbus device.

NodeWhat it isHas an IP?
PLCA controller with one sensor s and one actuator a. Its sensor is read by the MTU; its actuator is driven by rules.Yes
MTUThe master station — reads every PLC's sensor and sends commands. One per network.Yes
SwitchOne LAN segment. Everything connected to it shares a subnet and can talk directly.No
RouterJoins two switches into a WAN (two different subnets that still reach each other).Yes

3 Build it: add & wire

  1. Add nodes. Click + PLC, + MTU, + Switch, + Router — each appears on the canvas.
  2. Move anything. Press a node and drag it anywhere — free movement, no grid snapping. A single click (no drag) selects it.
  3. Connect. Click 🔗 Connect (it turns blue), then either drag from one node onto another, or click the first node then the second. A dashed line follows your cursor.
  4. Delete. Select a node and press Delete (or the 🗑 button). Esc cancels a half-drawn link.
Golden rule: connect each PLC and the MTU to a Switch. That puts them on one LAN where the MTU can reach them all. Use a Router only to join two switches.
Watch out: a direct PLC↔PLC or PLC↔MTU link is drawn as a dashed amber line. It is a point-to-point wire — if one node has several of them they fight over the same IP and only one works (you'll see reached 1/2 after a run). For normal networks, go through a Switch.

4 Addresses

Click a node to edit it in the Properties panel:

FieldWhat to put
idThe node's name, e.g. PLC1.
IPEverything on one switch shares a subnet: 10.0.1.1, 10.0.1.2, … and the MTU at 10.0.1.254.
seed (PLC only)The sensor's starting value, so rules fire predictably. 2 is "low", 5 is "high".

5 Control rules — one PLC drives another

In the Rules box, type one rule per line, then press Apply rules:

PLC1.s < 3 => PLC2.a open   # if PLC1's register s is below 3, set PLC2's register a

Each PLC has two Modbus registers: s (an input register the MTU reads) and a (a coil the MTU writes). This is cross-PLC control: the MTU reads one PLC's register and commands another's.

If you see every a=0 after a run: no rule fired. Either you added no rules, or the triggering sensor's seed is not below the threshold. Add rules, press Apply rules, and set the seed low (e.g. 2).

6 Run it — what actually happens

1 · Validate
structure + rules checked on the server
2 · Build on CORE
real nodes, links & Modbus devices
3 · Read back
per device: reached? sensor & actuator values

Validate checks everything and lists any problems in the Output panel. ▶ Run builds and runs it live, then reports for each PLC whether the MTU reached it and the read-back values (s = sensor, a = actuator). Export saves the config file; the same file runs from the terminal.

★ Worked example — run three PLCs

One MTU reads three PLCs on a switch; a control ring makes each PLC's low sensor open the next PLC's actuator.

  1. Add: + MTU, + Switch, then + PLC three times → PLC1 PLC2 PLC3.
  2. Wire to the switch: click 🔗 Connect, then drag each onto SW1 — MTU→SW1, PLC1→SW1, PLC2→SW1, PLC3→SW1. All links should be solid grey (no amber).
  3. Addresses: the defaults already fit (PLCs 10.0.1.1/2/3, MTU 10.0.1.254). Leave each PLC's seed at 2.
  4. Rules: paste into the Rules box, then Apply rules: 
    PLC1.s < 3 => PLC2.a open
PLC2.s < 3 => PLC3.a open
PLC3.s < 3 => PLC1.a open
  5. Run: press Validate (should say VALID), then ▶ Run.

Expected Output:

RUN ✓ started=true, reached 3/3 PLC1: reachable=true s=2 a=1 PLC2: reachable=true s=2 a=1 PLC3: reachable=true s=2 a=1

Every sensor is 2 (below 3), so every rule fires and every actuator opens (a=1). Now change one PLC's seed to 5 and run again: that PLC's rule no longer fires, and the actuator it targets stays a=0 — you can see the control logic working.

7 Terminal scenarios you can run (tested)

The GUI is optional — everything runs from the terminal. These examples were all executed on this machine; the output shown is what they actually print. First, once per boot, start the emulator and go to the project folder:

# start the CORE daemon (asks for your password, once per boot)
sudo systemctl start core-daemon
cd /home/abdul/claudeProjects/Research-Papers/SCADATestbed/scadavt

All commands below use the small wrapper ./scadavt.sh (it sets the environment and picks the right Python for you).

Scenario A · your first network — one MTU, one switch, two PLCs

Save this as /tmp/hand.json — it is the whole network (two Modbus-register PLCs on one switch, with one control rule):

{
  "name": "my-first-net",
  "control": { "placement": "mtu" },
  "mtu": { "id": "MTU", "ip": "10.0.1.254" },
  "devices": [
    { "id": "PLC1", "ip": "10.0.1.1", "protocol": "modbus", "seed": 2.0,
      "registers": [
        { "id": "s", "area": "input_register", "data_type": "float32", "initial": 2.0 },
        { "id": "a", "area": "coil", "data_type": "bool", "owner": "mtu" } ] },
    { "id": "PLC2", "ip": "10.0.1.2", "protocol": "modbus", "seed": 9.0,
      "registers": [
        { "id": "s", "area": "input_register", "data_type": "float32", "initial": 9.0 },
        { "id": "a", "area": "coil", "data_type": "bool", "owner": "mtu" } ] }
  ],
  "switches": [ { "id": "SW1" } ],
  "links": [
    { "a": "MTU",  "b": "SW1", "a_ip": "10.0.1.254" },
    { "a": "PLC1", "b": "SW1", "a_ip": "10.0.1.1" },
    { "a": "PLC2", "b": "SW1", "a_ip": "10.0.1.2" }
  ],
  "logic": [
    { "id": "r1",
      "if":   [ { "device": "PLC1", "register": "s", "op": "below", "value": 3.0 } ],
      "then": [ { "device": "PLC2", "register": "a", "set": 1 } ] }
  ]
}

Each link connects a node to the switch (PLC1 → SW1, MTU → SW1, …). Then:

./scadavt.sh validate /tmp/hand.json
./scadavt.sh run /tmp/hand.json --live
OK — config is valid (structure + semantics) session started=True MTU reached 2/2 devices PLC1 reachable=True s=2.0 a=0.0 PLC2 reachable=True s=9.0 a=1.0

PLC1's register s=2 is below 3, so the rule fired and set PLC2's coil a=1 — the MTU read PLC1 and commanded PLC2, all over real Modbus.

Scenario B · a bigger LAN — 3 PLCs on one subnet, no file writing

scaffold builds a ready network for you (a cross-PLC ring); then run it:

./scadavt.sh scaffold --plcs 3 -o /tmp/lan.json
./scadavt.sh run /tmp/lan.json --live
MTU reached 3/3 devices PLC1 reachable=True s=2.0 a=1.0 PLC2 reachable=True s=5.0 a=1.0 PLC3 reachable=True s=2.0 a=0.0

A control ring: each PLC whose s is low opens the next PLC's a.

Scenario C · a WAN — 6 PLCs across two subnets joined by a router

--per-subnet splits the PLCs over several /24 subnets; a router joins them (a WAN). The MTU still reaches and controls every PLC across the router:

./scadavt.sh scaffold --plcs 6 --per-subnet 3 -o /tmp/wan.json
./scadavt.sh plan /tmp/wan.json          # see the nodes/links (SW1, SW2, R1 router)
./scadavt.sh run /tmp/wan.json --live
MTU reached 6/6 devices PLC1 reachable=True s=2.0 a=0.0 PLC2 reachable=True s=5.0 a=1.0 PLC3 reachable=True s=2.0 a=0.0 PLC4 reachable=True s=5.0 a=1.0 PLC5 reachable=True s=2.0 a=0.0 PLC6 reachable=True s=5.0 a=1.0

PLC3 (subnet 1) opening PLC4 (subnet 2) proves cross-subnet control over the router.

💡
To put specific PLCs on specific subnets by hand, give them IPs in different /24s (e.g. 10.0.1.x and 10.0.2.x), add a second switch and a router, and link each switch to the router (see the scaffolded /tmp/wan.json for the exact shape).

8 See the traffic — capture & open in Wireshark

Nothing is hidden: the Modbus packets between the MTU and the PLCs are real and you can watch them. This run captures them to a .pcap you open in Wireshark.

Capture — run a 3-PLC network that records the MTU's traffic to a pcap:

SCADAVT_DIR=$PWD SCADAVT_NODE_PY=$PWD/.venv/bin/python \
  /opt/core/venv/bin/python tools/live_core_network.py --plcs 3

It prints an evidence folder, e.g. evidence: /tmp/scadavt_net_XXXX/evidence. The capture is mtu_modbus.pcap in there.

Open it in Wireshark:

wireshark /tmp/scadavt_net_*/evidence/mtu_modbus.pcap   # GUI
# or, in a terminal, without the GUI:
tcpdump -nr /tmp/scadavt_net_*/evidence/mtu_modbus.pcap | head
10.0.1.254.52134 > 10.0.1.1.502: Flags [P.], length 12 # MTU -> PLC1 request 10.0.1.1.502 > 10.0.1.254.52134: Flags [P.], length 13 # PLC1 -> MTU reply

Port 502 is Modbus/TCP. In Wireshark type modbus in the filter bar to decode each read/write (function code, register address, value) — you can see exactly which register the MTU read and which coil it wrote.

💡
Live capture instead of a file: keep a session up and sniff a node directly — run a scenario with the tool left running, then in another terminal attach to a node's namespace with CORE's vcmd/coresendmsg and run tcpdump -i eth0 tcp port 502 -w live.pcap, then open live.pcap in Wireshark. The pcap method above is the simplest and needs no extra tools.

9 Troubleshooting

You see…Why / fix
reached 1/2 (not all reached)A device is not on a shared LAN. Connect every device to a Switch and give them IPs in the same subnet; avoid direct device↔device (amber) links.
All a=0 after a runNo rule fired — add rules and Apply rules, and make sure the triggering sensor's seed is below the threshold.
INVALID on ValidateRead the listed issues — usually a duplicate IP, a link to a missing node, or a rule referencing an element that doesn't exist.
RUN failed (503)The service can't reach CORE. Start the daemon (sudo systemctl start core-daemon) on a host with CORE, or set SCADAVT_CORE_PYTHON.
Can't reach the serviceCheck the Service base field (blank = same origin) and, for a remote service, the Auth token.
